# FDR-016: Voice Calls

**Status:** Active
**Last reviewed:** 2026-08-01

## Overview

Rooms support real-time voice conversations with optional camera video and screen/window/tab sharing. Browser-tab audio is published with the screen share when the selected browser and capture surface provide it. Starting or joining a call opens a central room workspace, while a single global call dock keeps the current session and its controls available across rooms and servers. Audio and video are routed through LiveKit (an external WebRTC service); Towk handles authorization, participant state, navigation, and presentation.

## Behavior

- Members see call actions in the canonical room header and room list when LiveKit is configured. Members and Files remain the only room-sidebar panels.
- Every room-header, room-list, direct-message, notification, and dock entry point submits one centralized join intent. Duplicate intents coalesce, navigation finishes before admission, and a newer room intent supersedes delayed work from an older one.
- A successful or recovering local session selects the room's central Call surface. Messages remains mounted but inert, and the user can switch between Messages and Call without leaving. Admission failure returns to Messages without a phantom dock or stale Call surface.
- With no screen share, the central workspace uses a stable, container-sized gallery. It bounds mounted tiles, paginates when the available width or height is insufficient, and does not reorder the gallery for short speaking-level changes.
- A screen share becomes the featured stage with a bounded filmstrip. Concurrent shares remain represented and selectable; a manual selection is stable when another share appears and falls back deterministically when the selected track ends. Shared content uses aspect-ratio-preserving containment.
- An account may keep up to two browser/device connections in the same call. A second connection must explicitly choose between joining as a companion or transferring the call. Companion mode starts with both the microphone and all incoming call audio muted to prevent echo, while the camera remains available and screen sharing remains available only when the browser exposes it; either audio direction can be enabled afterward. Transfer disconnects every older connection for that account and continues on the new device. A third connection can only transfer or cancel.
- When two connections from one account are present, participant cards remain connection-distinct and show localized Device 1 / Device 2 badges below the participant name so narrow call panels preserve the name. Account-level actions such as opening a profile or starting a direct message still target the underlying account, not the media-session identity.
- The workspace measures its actual container after navigation, sidebars, system bars, zoom, and PWA window sizing. Browser fullscreen and per-feed fullscreen remain explicit viewer-local actions rather than alternative room layouts.
- Camera and screen-share tiles expose feed-fullscreen and audio controls on hover-capable devices, and keep those controls visible on touch devices. Feed fullscreen is local to the viewer's browser: Towk uses the native Fullscreen API when available and falls back to a safe-area-aware full-viewport viewer when the browser does not expose it, including iPhone WebKit. For another account, mute remains local to the viewer and does not change server state or other participants' audio. A sibling connection from the same account instead exposes separate controls for that device's microphone and incoming call audio. Local participant tiles expose the viewer's own microphone mute.
- While the viewer has a joining, connected, or recovering session, exactly one global dock is hosted: in the left shell while that shell is open, otherwise as a floating compact dock. It identifies the room and server and provides incoming audio, microphone, camera, screen share, devices, return, and leave controls.
- Dock and operating-system actions re-resolve the owning server store and call generation when invoked. They never target the currently viewed server implicitly or retain a disposed authentication store.
- While any call is connected, compatible browsers hold a screen Wake Lock only while Towk is visible, classify the audio session as duplex `play-and-record`, publish call metadata and microphone/camera state through Media Session, and expose operating-system actions for mute, camera, and hang-up. A pending PWA update never reloads during join, connection, or recovery; the user can schedule it for after the call. Video and screen-share tiles offer standards-based Picture-in-Picture with the WebKit presentation fallback where available. The enhanced Web Audio microphone graph is detached before the document is hidden and restored after it becomes visible so a suspended `AudioContext` cannot silence the sender. The original browser microphone track stays published while hidden, but continued background capture remains an operating-system and browser decision rather than a portable PWA guarantee.
- Other rooms with an active call replace the normal room/DM icon with an accent call action so members know a conversation is active; clicking the dedicated action navigates, joins the exact call generation, and opens the central Call surface without changing the room-link semantics.
- Message author names show a compact call presence icon when the author is in the current room's active call: phone for voice-only participants, video camera when the viewer has joined the LiveKit call and can see an active camera track.
- A member's join/leave updates active call indicators and participant lists, but call lifecycle and participant transitions are not shown as room timeline messages. Explicit user intent is recorded immediately, and LiveKit webhooks/reconciliation confirm or correct the active participant projection.
- Losing room membership also removes the user from the room's active call. This includes voluntarily leaving the room, being removed by a moderator, being banned, and account-deletion cleanup. Towk records the call leave from the membership transition and best-effort asks LiveKit to disconnect the participant; if that LiveKit removal fails, the room membership change still succeeds and reconciliation can catch up later.
- Joined call participants hear fixed synthesized cues from durable participant join/leave events, including their own join/leave events and other participants in the same active call. These call cues are separate from configurable notification sounds and do not use notification sound filters; `CallEndedEvent` does not play a separate cue.
- Microphones request browser echo cancellation, noise suppression, automatic gain control, voice isolation, and mono capture, then use Opus DTX plus RED. The browser and operating system keep ownership of Bluetooth HFP/BLE routing and its capture clock. Users can disable or re-enable noise reduction, automatic gain, and echo cancellation from the call device menu; changes are applied to the already-published source track before the effective status is recalculated. A same-origin AudioWorklet/WASM enhancement adds RNNoise at 48 kHz or SpeexDSP at another matching source/context rate, including when the browser reports its own basic suppression active. Bluetooth and narrowband routes remain native-only to avoid adding a second capture clock; hiding the document also detaches the enhanced graph before browsers suspend Web Audio. Towk does not force a 48 kHz capture preference.
- Cameras request an ideal 4:3 1280 × 960 at no more than 30 FPS instead of asking for a 16:9 crop. When the browser exposes the standard `resizeMode` constraint, Towk requests `none` so a 4:3 mobile sensor is not cropped before publication; a driver-specific rejection retries once without that hint. Camera and screen video are rendered with aspect-ratio-preserving containment. Mobile Camera2 labels are normalized to front, rear, ultra-wide, or telephoto names, and a local video tile offers one-touch lens switching when several cameras are exposed.
- The first join starts a call session, creates fresh per-call E2EE key material, and records durable call lifecycle facts. The final leave ends the call, records the end fact, and shreds the call key.
- Hanging up commits the exact connection's leave, asks LiveKit to evict only that media identity, clears the participant from everyone else's view, and returns the source room to Messages. Sibling devices owned by the same account remain in the call.
- A temporary network interruption keeps the participant's intent to remain in the call. Towk shows an accessible recovery notice, retries automatically every 2.5 seconds without an attempt limit, and keeps hang-up available. Native LiveKit recovery preserves and republishes active tracks; if that session can no longer be resumed, Towk obtains fresh call credentials and rejoins automatically while the user is still authorized.
- New clients always enable LiveKit E2EE before connecting. Towk distributes a KMS-backed per-call shared key with the LiveKit join token; the raw key is never written to EVT and is shredded when the call ends.
- Screen sharing requests browser-tab audio, keeps full-system audio out of the picker, and confirms whether the browser supplied an audio track. A shared-audio indicator is visible on the screen tile. If no audio track is available, Towk explains that Chrome or Edge desktop users must select a browser tab and enable tab audio in the picker.
- Screen video publishes a 1080p30 top layer at up to 5 Mbit/s plus a 720p30 simulcast layer capped at 1.5 Mbit/s. The explicit high-frame-rate mode is capped at 8 Mbit/s for 1080p60. While a local screen is shared, an active local camera remains live on its low spatial layer and returns to full quality when sharing stops. LiveKit adaptive stream and dynacast select the useful layer, while balanced degradation may trade resolution for motion instead of holding a frozen full-resolution frame on a constrained uplink.
- Towk capability-checks `MediaDevices.getDisplayMedia` before capture. Current mobile web engines on Android and iOS do not expose this API to PWAs, so the screen-share control stays compact and visibly unavailable; tapping it shows a temporary explanation instead of opening a picker that inevitably fails. Native Android MediaProjection and iOS ReplayKit capture are outside a web PWA's API boundary.
- Screen-share state is LiveKit track state only. Users who have not joined the call still see who is in the active call, but they do not see whether a participant is sharing a screen.
- When LiveKit is not configured on the server, all voice UI is hidden — no button, no panel, no indicator.

## Design Decisions

### 1. Call lifecycle and join/leave are durable room facts with internal source

**Decision:** `CallStartedEvent`, `CallParticipantJoinedEvent`, `CallParticipantLeftEvent`, and `CallEndedEvent` are persisted in the room EVT aggregate keyed by room ID, on `evt.room.{roomId}.call_started`, `evt.room.{roomId}.call_joined`, `evt.room.{roomId}.call_left`, and `evt.room.{roomId}.call_ended`. Explicit frontend join/leave writes use source `USER`; LiveKit webhook writes use source `LIVEKIT`; reconciliation writes use source `RECONCILIATION`. Public APIs expose call state without the internal source or E2EE key ref. Call facts drive active call state, live indicators, and key lifecycle, but are hidden from normal room history.
**Why:** Calls are realtime/audit facts that should survive process restarts and be delivered through the same durable live EVT path as other room facts. Towk's product model treats calls as always happening inside a room, with at most one active call per room. Rooms are intentionally cheap coordination spaces, so future private, temporary, or non-public calls can use short-lived rooms and inherit room membership, authorization, naming, visibility, and live-delivery behavior instead of introducing a separate call-membership model. Keeping source internal lets projections distinguish optimistic user intent from media-server observation without adding public API surface.
**Tradeoff:** Duplicate user/LiveKit/reconciliation reports are collapsed at the call-state write boundary when they do not change participant state. A real join, leave, and later rejoin still records each transition as a distinct call session. The model uses the call projection's per-room applied sequence as the OCC token against `evt.room.{roomId}.>` so lifecycle and participant transitions are guarded by the room aggregate boundary across replicas. The design deliberately favors room-scoped calls over independent call aggregates; if calls later need their own durable lifecycle beyond the room boundary, new writes may need to move to a call aggregate while replaying legacy room-scoped facts.

### 2. Active call state is projection-backed and reconciled

**Decision:** Active participant snapshots and the active call session come from a call-state model/projection over durable call facts, not from `MEMORY_CACHE`. User joins can create pending/optimistic state; LiveKit and reconciliation facts confirm or correct it. Towk includes the active Towk `callId` in the LiveKit room name so LiveKit webhooks and reconciliation snapshots are applied only to the matching call session. On startup and periodically, Towk compares active LiveKit rooms/participants to the projection and appends reconciliation facts for mismatches. If LiveKit cannot list rooms/participants for three consecutive elected reconciliation cycles, Towk ends all projected active calls with reconciliation facts; before that threshold it defers cleanup. If LiveKit reports a room in `ListRooms` but returns not-found when participants are listed, Towk treats that room as gone/empty and continues reconciling other rooms.
**Why:** The UI needs current participant state, but it should not depend only on volatile KV state or only on historical replay. EVT gives durable audit/live delivery, while LiveKit reconciliation keeps "who is connected now" grounded in the media server.
**Tradeoff:** The projection can briefly show optimistic state before LiveKit or reconciliation corrects it. If LiveKit reports the same already-active transition, the duplicate report is skipped instead of appending another public call event. A sustained LiveKit listing outage can end active calls after the shared failure threshold, favoring eventual UI recovery and unblocking new sessions while avoiding immediate cleanup for transient API failures. Multiple replicas may reconcile concurrently; call transition facts are OCC-gated on the room aggregate and rechecked after conflicts.

### 3. Graceful degradation when LiveKit isn't configured

**Decision:** When LiveKit credentials are absent, the call APIs return null/empty and the frontend hides the entire voice UI.
**Why:** Self-hosters who don't want to run LiveKit (or haven't yet) shouldn't see dead UI affordances. Hiding the surface entirely is clearer than disabled buttons. See ADR-009.
**Tradeoff:** Operators have to know LiveKit setup exists. Documented in setup guides.

### 4. Audio tracks must be explicitly attached

**Decision:** The frontend listens for `RoomEvent.TrackSubscribed` and calls `track.attach()` to wire LiveKit microphone and screen-share audio into a hidden `<audio>` element. On leave or `TrackUnsubscribed`, it calls `track.detach()`.
**Why:** LiveKit delivers audio data over WebRTC, but the browser doesn't autoplay it without an attached element. Without explicit attach, the UI looks like everything works — participant rings even animate — but nobody hears anything. The pattern lives in `apps/frontend/src/lib/state/server/voiceCall.svelte.ts`; any refactor that touches LiveKit subscription handling needs to keep the `track.attach()` / `track.detach()` calls intact.
**Tradeoff:** A subtle requirement that's easy to miss when refactoring; both microphone and `ScreenShareAudio` publications must keep this attachment path.

### 5. Speaking indicators follow LiveKit events and use a restrained accent pulse

**Decision:** Participant cards copy the complete LiveKit speaking snapshot on every `RoomEvent.ActiveSpeakersChanged` event and update their accent outline in the same browser event turn. Every participant marked as speaking remains highlighted independently, so concurrent speakers are visible together. Active outlines use a restrained transform-and-opacity pulse; reduced-motion clients keep the static outline without the pulse. Speaking indicators continue to reuse LiveKit audio levels and never open a second microphone-analysis `AudioContext`.
**Why:** Event-driven propagation avoids adding the previous state-cache and component polling windows after LiveKit has already detected speech. Updating the complete snapshot preserves simultaneous speakers, while limiting animation to compositor-friendly properties keeps the feedback fluid across compact and large call layouts.
**Tradeoff:** LiveKit and the media path still own speaker-detection latency, so the frontend cannot guarantee an instant outline before that event arrives. The accent outline is more prominent than a neutral glyph; reduced-motion clients intentionally receive state feedback without motion.

### 6. Screen sharing is joined-client LiveKit track state

**Decision:** Screen/window/tab sharing uses LiveKit's browser publishing path and is represented by `Track.Source.ScreenShare` plus optional `Track.Source.ScreenShareAudio` on joined clients. The capture request prefers a browser tab, excludes the current Towk tab and full-system audio, and keeps Chrome's in-picker tab switching available. The publish profile uses a 1080p30/5 Mbit/s top layer, a 720p30/1.5 Mbit/s fallback and balanced degradation; the opt-in 1080p60 profile is capped at 8 Mbit/s. A simultaneous local camera is capped to its low spatial layer for the duration of the share, then restored. Browser-tab audio uses the same mono speech Opus profile as the microphone so both tracks keep identical codec parameters inside the bundled peer connection. Towk also keeps LiveKit's startup bitrate hint common across bundled video sections, caps it at 1 Mbit/s and removes an inconsistent SFU echo before applying a remote answer. Towk does not persist separate screen-share events, add public API fields, or expose screen-share state to call observers before they join.
**Why:** Screen sharing is media-session state, and the existing durable room facts already answer the server-owned question of who is in the call. Keeping video and optional tab audio inside LiveKit avoids durable state that can become stale when browser capture ends. Excluding system audio prevents remote call voices from being captured back into the call, while the browser permission picker remains the authority for every capture.
**Tradeoff:** Non-joined observers know a call is active and who is in it, but not whether someone is sharing. Browser-tab audio favors call stability over stereo music fidelity. Tab audio capture is currently limited to Chromium desktop browsers and compatible surfaces; Firefox and Safari can still publish screen video. Android and iOS PWAs cannot bridge to native screen-capture APIs, so Towk reports the limitation instead of claiming mobile support.

The compatibility boundary is tracked against [MDN `getDisplayMedia`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia), [MDN browser compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json), and [Chrome's screen-sharing controls](https://developer.chrome.com/docs/web-platform/screen-sharing-controls/). Because browser support is volatile, these sources must be rechecked before broadening the support claim.

### 7. Call presentation is a central room surface, not a sidebar mode or separate route

**Decision:** Each room has session-only Messages and Call primary surfaces under one canonical room header. The Call surface occupies the normal timeline/composer area; Members and Files remain independent sidebars. The scene computes a bounded gallery or featured-share filmstrip from its observed container and paginates off-page video tiles.
**Why:** Calls remain room-scoped context while receiving enough width and height for readable media. The same model works on phone, tablet, desktop, and installed-PWA windows without treating a narrow utility sidebar as a conferencing canvas.
**Tradeoff:** The scene is intentionally not persisted across reload and never auto-joins. Messages remains mounted to preserve drafts and scroll state, so it must be made inert and must not advance read state while Call owns attention.

### 8. Fullscreen and local mute are viewer-local controls

**Decision:** Individual media tiles use the browser Fullscreen API when it is available. If the API is missing, disabled, or rejects the request, Towk opens the same LiveKit track in an application-owned fixed viewer sized with dynamic viewport units and safe-area insets. Touch devices keep the media actions visible instead of requiring hover. The desktop call pane continues to use the browser Fullscreen API. Local mute changes only this viewer's local audio: remote participants are muted through LiveKit remote participant volume, and local participant tiles reuse the viewer's microphone mute.
**Why:** Fullscreen and "I don't want to hear this feed/user right now" are personal presentation choices. They should not create durable call facts, alter room state, or surprise other participants. iPhone does not expose arbitrary-element Fullscreen API support, so a web-owned full-viewport viewer is required for a reliable PWA path.
**Tradeoff:** The fallback fills the web app viewport but cannot hide Safari browser chrome because iPhone does not grant that capability to arbitrary web content. Installed standalone PWAs use the available app viewport. Local mute is intentionally not visible to other participants and does not change the remote participant's published mute state. Users need to distinguish it from the normal microphone mute indicator.

### 9. Test endpoints bypass webhook validation in build-tag mode

**Decision:** E2E tests use special `/webhooks/test/call-join` and `/webhooks/test/call-leave` endpoints that skip HMAC validation and call the core methods directly. Available only with `-tags test_endpoints`.
**Why:** Real LiveKit isn't realistic to run in CI, but webhook flow is exactly the thing E2E tests need to exercise. Build-tag gating keeps the endpoints out of production. See ADR-020.
**Tradeoff:** Two webhook entry points (real + test); test ones are well-isolated and trivially removable from prod builds.

### 10. E2EE keys are KMS-backed per-call secrets

**Decision:** `voiceCallToken` returns both `token` and `e2eeKey`. The first join for a room creates a new call ID and per-call E2EE key through Towk's KMS boundary, stores the raw key in `ENCRYPTION_KEYS` under `call.e2ee.{callId}`, and records only the key ref in `CallStartedEvent`. The final leave records `CallEndedEvent` and shreds the key ref. The frontend creates an `ExternalE2EEKeyProvider`, configures the LiveKit E2EE worker, sets the key, enables E2EE, then connects.
**Why:** LiveKit E2EE key generation/distribution is application responsibility. Towk already authorizes token access by room membership, so the token resolver is the narrow place to distribute the shared call key. Keeping the raw key out of EVT and normal backups avoids turning event-log copies into permanent decrypt material for captured media.
**Tradeoff:** Always-on E2EE breaks media compatibility with older clients that do not enable E2EE. Restoring a backup without `ENCRYPTION_KEYS` cannot recover active call keys; active calls should be considered interrupted across such restores.

### 11. Voice capture combines portable browser constraints with local suppression

**Decision:** Every microphone track requests `echoCancellation: true`, `noiseSuppression: true`, `autoGainControl: true`, `voiceIsolation: true`, and mono capture by default. These remain non-mandatory media constraints so a browser or device that cannot honor one preference does not block the call. The device menu exposes per-call controls for noise reduction, automatic gain, and echo cancellation; changing a control while the microphone is live applies the updated constraints directly to the published source track through the serialized input queue, then reconciles the enhanced processor, while changing it muted applies the preference to the next capture. No sample rate is requested: the browser and operating system choose the route-compatible capture clock, including Bluetooth HFP/BLE communication profiles, and WebRTC performs codec conversion. On visible, non-Bluetooth mono routes with a source rate of at least 32 kHz matching the LiveKit audio context, Towk attaches the self-hosted processor from `apps/frontend/src/lib/audio/backgroundNoiseSuppression.ts`: RNNoise handles 48 kHz and SpeexDSP handles other matching rates. When a browser omits optional `channelCount` or `sampleRate` members from `MediaTrackSettings`, a confirmed non-Bluetooth route may use the AudioContext clock instead of being incorrectly excluded. When WebKit also exposes an opaque or non-correlatable device ID, Towk uses a positively identified source-track label such as an iPhone, Mac built-in, USB, wired, or known Bluetooth microphone as additional route evidence; generic and processor-generated labels remain unknown. This enhancement is allowed on compatible built-in mobile routes and may supplement browser-native suppression. It never adds software gain on top of confirmed native AGC. Bluetooth identity is reconciled from the source track, LiveKit's active route, and the selected enumerated device so an opaque Android source ID cannot accidentally enable the second Web Audio clock. A logical `default` or `communications` route may use enhanced suppression when the current input inventory contains no Bluetooth device; if any Bluetooth input is visible, the logical route remains native-first because its physical clock can change behind the stable ID. Confirmed Bluetooth, narrowband, hidden-document, and explicit source/context-mismatch routes stay on the native track. If an input route or system-managed mobile output changes while the processor is attached, Towk first removes the processed destination to reveal the current capture label, then either restores enhanced processing on the compatible source or leaves the new Bluetooth/profile route native. If enhanced processing cannot attach, Towk keeps the microphone live, retries reconciliation on later route/lifecycle events, and reports the reduced capability. The worklet and WASM files are emitted with the frontend and fetched from the Towk origin only. Speaking indicators reuse LiveKit audio levels and do not open a second microphone-analysis `AudioContext`.

Audio input and output changes run through separate serialized client queues so capture toggles, capture restarts, sink changes, and playback resumption cannot overlap. The incoming-audio toggle synchronizes both LiveKit track volume and the attached media elements' hard mute state; this preserves the control on iOS, where script-driven media volume is not a portable mute mechanism. Selecting the already active route is a no-op, avoiding an unnecessary Bluetooth communication-profile restart. The visible selection follows LiveKit's active route and replaces a device ID that disappeared. If an exact microphone route disappears while muted or during a fresh network-recovery session, Towk re-enumerates the available inputs, moves the publication to a surviving route, and only then retries capture. Mobile browsers may instead keep the logical `default` ID unchanged or briefly expose no inputs while the operating system moves between Bluetooth and built-in audio. In that case Towk drops the stale exact constraint, restarts an existing muted track when present, and reacquires the operating-system route without forcing a device ID. If a generic Bluetooth route appears and the user has not explicitly selected another route in this call, Towk prefers it for call audio because headset users generally expect microphone and output to follow the connected headset. If the user chooses speakerphone, earpiece, system default, or another named route, that explicit choice wins until the route disappears or the call ends. If LiveKit exhausts its native route replacement and automatically mutes the track, Towk keeps that state distinct from an intentional mute, shows a microphone-recovery notice, and retries after 1, 2, and 4 seconds. A media-device change forces an immediate attempt, while the bounded schedule also covers mobile browsers that expose no `devicechange` event. Explicit mute cancels recovery, and three failed background attempts stop the timer so revoked permissions cannot create an unbounded capture loop. Selecting a different microphone while this recovery state is visible immediately retries capture on the chosen route, including after the background schedule has ended. If processor detachment fails after its output track has stopped, native capture is reacquired so the sender cannot remain attached to silence. Towk reconciles processing after `MediaDevicesChanged` and `ActiveDeviceChanged`; a low-frequency settings fingerprint also catches an audio clock or route change when a mobile browser emits neither event. Opening the menu re-enumerates devices because some Android browsers expose `enumerateDevices()` without `devicechange`. Where the standards-based `selectAudioOutput()` picker exists, it is invoked directly from the user's click before any other asynchronous work; elsewhere the operating system keeps control of speaker, Bluetooth, and headset routing. Generic `default`, `communications`, empty, and opaque device labels are rendered as stable localized names while useful desktop hardware labels remain visible. Generic mobile speakerphone, earpiece, and Bluetooth routes are presented by intended call usage rather than raw platform names.

**Why:** Chromium and Firefox expose the standard noise-suppression and automatic-gain constraints, while WebKit may keep final DSP settings hidden. A true setting proves that the constraint was applied, not how much stationary noise it removes, so compatible routes also receive the measurable local suppression layer. Native processing remains authoritative for echo cancellation, confirmed AGC, Bluetooth routing, and the capture clock. Keeping the enhancement local preserves call E2EE and avoids a cloud dependency, external audio upload, or runtime CDN. The served CSP permits only the narrow `wasm-unsafe-eval` source expression required for WebAssembly compilation; JavaScript `unsafe-eval` remains disallowed. Combining LiveKit's platform-specific device recovery with route events, a bounded settings check, and an on-demand enumeration covers browsers that expose only a subset of the media-device APIs without pretending a web app can select a native Bluetooth profile.

**Tradeoff:** Browser media constraints are preferences, and web APIs do not expose a portable Bluetooth transport/profile identifier. Towk therefore cannot prove a transport profile from arbitrary localized labels. It conservatively recognizes explicit Bluetooth and hands-free labels plus common wireless-earbud product families; an unrecognized vendor label can still remain ambiguous. Missing source settings are not treated as proof of incompatibility, but every enumerated Bluetooth identity remains authoritative and disables the additional graph. An explicit device choice is attempted with an exact constraint, but that constraint is not retained as an absolute requirement after the device disappears. Permission-denied and device-in-use failures from an explicit action are surfaced without silent rerouting; an already automatic route-recovery sequence remains visible and bounded. The one-second route fingerprint reads only local `MediaTrackSettings`; it creates no audio graph, records no audio, and does no work unless the effective settings change. A route probe briefly rebuilds the local processing graph, so it is limited to actual input inventory, active-route, system-managed output, or source-settings changes rather than periodic recreation. WebKit bug 244203 remains an upstream warning for older or affected Web Audio capture clocks; the matching-clock gate, native fallback, and physical-device acceptance remain mandatory.

The standards boundary is defined by [Media Capture and Streams](https://w3c.github.io/mediacapture-main/), [Web Audio](https://www.w3.org/TR/webaudio-1.1/), and the [Audio Output Devices API](https://w3c.github.io/mediacapture-output/). Current compatibility data records `setSinkId()` as unavailable in Chrome and Firefox on Android. Native Android couples a selected communication output with its matching input through [`AudioManager.setCommunicationDevice()`](<https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo)>); native Apple platforms perform the equivalent HFP coupling through [`AVAudioSession`](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetooth). Those native APIs are not callable from an ordinary Towk web page.

### 12. Call participation separates account identity from connection identity

**Decision:** Each call connection has an opaque participant ID derived from the authenticated account and a browser-session instance ID. Durable join/leave facts, public call snapshots, realtime events, LiveKit identities, webhooks, and reconciliation carry that connection identity plus a display-only device index. Admission is protected by room-aggregate OCC: the first connection joins directly, a second requires an explicit companion or transfer mode, and no account may exceed two projected connections. A leave with a participant ID removes exactly one connection; legacy or room-membership leave facts without one remove every connection for that account.
**Why:** LiveKit requires unique participant identities within a room, while Towk must still authorize and render both connections as one account. Keeping the account ID in immutable token metadata lets webhooks and reconciliation recover the ownership relation without trusting mutable participant metadata. Connection-scoped facts prevent one tab's disconnect from erasing its sibling, and the two-device cap bounds echo-prone or accidental duplicates.
**Tradeoff:** Existing clients that omit the browser-session ID retain the former single-device transfer behavior. Device 1 / Device 2 are stable slots within the current projected call, not hardware names. LiveKit eviction after transfer is best effort, so the durable exact leave event also tells a still-connected old client to disconnect; periodic reconciliation evicts any connection-scoped identity that is no longer durably admitted instead of allowing it to recreate membership. If the transferred account is alone in the call, Towk rotates the call ID and E2EE key atomically so a delayed finish event for the emptied old LiveKit room cannot remove the replacement device.

### 13. Sibling-device audio control is connection-scoped and ephemeral

**Decision:** Two active connections owned by the same authenticated account exchange explicit desired microphone and incoming-audio states through a versioned LiveKit participant RPC. Voice tokens explicitly allow data publishing while denying participant-owned metadata updates. The receiver authorizes every request by comparing server-authored account and participant IDs from that immutable token metadata, applies idempotent state changes locally, and returns a revisioned snapshot. State changes are not persisted as room facts. Requests from another account or from metadata that is not bound to the caller's LiveKit identity are rejected.
**Why:** A companion device must be controllable without granting one user authority over another participant or turning browser-local playback into durable server state. Explicit desired states avoid double-toggle races, and revision numbers prevent delayed state notifications from overwriting newer UI state.
**Tradeoff:** Both sibling connections must support the RPC method before remote controls become available. An older or disconnected client leaves the controls unavailable and the call itself usable. Browser autoplay and media permissions remain authoritative, so an unmute request can fail and is reported without pretending the target changed.

### 14. Network recovery follows user intent, not a finite retry budget

**Decision:** Once a participant has joined, LiveKit's native resume and full-reconnect path retries immediately and then every 2.5 seconds without a maximum attempt count. A browser `offline` signal exposes the recovery state immediately, before the WebRTC timeout; a matching `online` signal clears that early notice only when the current LiveKit room is still connected. Towk exposes the reconnecting state in the call panel and current-user call card, disables media mutations while transport state is uncertain, and leaves hang-up enabled. If LiveKit reaches a terminal network/session failure, Towk keeps the local call intent, records or renews the participant projection, obtains a fresh five-minute join token and current E2EE key, and creates a new encrypted connection on the same retry cadence. Microphone restoration uses the selected route when it still exists, an enumerated fallback when it does not, and the operating-system default when the browser exposes no stable input identity during the handoff. Intentional leave, duplicate identity, participant removal, room deletion, and authorization failures stop recovery.
**Why:** Mobile and intermittent networks can disappear longer than a fixed SDK retry window. The user should not have to watch the connection or press Join again, while an explicit decision to leave or an authorization change must remain authoritative.
**Tradeoff:** Native recovery is the preferred path because it republishes existing microphone, camera, and screen-share tracks. A fresh encrypted connection can reacquire microphone and camera access when browser permission remains available. Browsers require a new user gesture for some screen-capture recovery paths, so a terminal session replacement may restore the call while leaving a rejected screen-share restart visibly stopped; ordinary transport recovery does not have that limitation.

### 15. Screen-share diagnostics are opt-in and browser-local

**Decision:** Joined screen-share tiles expose a persistent diagnostics action outside the video surface. Opening it polls the selected local sender or remote receiver `RTCStatsReport` every two seconds and keeps at most 30 samples in component memory. The panel normalizes standards-based RTP, codec, transport and candidate-type fields; derives interval bitrate, frame rate, loss and drop rates from counter deltas; distinguishes sender congestion from receiver playback metrics; excludes auxiliary RTX/FEC streams from media-layer totals; and reports unavailable fields as unknown instead of inventing values. It never reads candidate addresses, calls a Towk API, emits telemetry or persists history.
**Why:** A screen-share quality problem can originate at capture, encoding, congestion control, transport or decoding. Giving both sides the same opt-in evidence makes those stages distinguishable without weakening call E2EE or adding server-side observation. Keeping collection dormant while the panel is closed avoids continuous `getStats()` work for users who do not need diagnostics.
**Tradeoff:** WebRTC statistics remain best-effort browser diagnostics rather than a stable Towk API. Browsers omit or rename some optional fields, initial rate values need a second counter sample, and health labels are indicative rather than a service-level guarantee. The implementation follows the [W3C WebRTC Statistics API](https://www.w3.org/TR/webrtc-stats/) and LiveKit's track-level stats access, while preserving explicit unavailable states for engine differences.

### 16. Installed-app call controls remain viewer-local

**Decision:** A connected call requests a screen Wake Lock while the document is visible, re-acquires it after visibility returns, and releases it on hide, hang-up, or component destruction. Where the Audio Session API exists, Towk temporarily selects `play-and-record` so the platform treats the session as duplex communication and restores the prior type on hang-up. Media Session publishes room/server metadata plus call-specific hang-up, camera, and microphone actions when supported. Before the document becomes hidden, Towk removes its enhanced Web Audio graph and keeps the browser-native microphone track published; after visibility returns, it reapplies the selected constraints and enhancement. Video tiles enter standard Picture-in-Picture from an explicit click, with WebKit's video presentation mode as a fallback.
**Why:** Calls should behave like an installed communication app without bypassing browser permission and activation rules. Audio Session provides the relevant call-audio category on supporting WebKit platforms, while removing the optional `AudioContext` graph prevents page lifecycle suspension from replacing a working source with silence. Keeping these integrations in the client preserves the existing LiveKit and E2EE boundary.
**Tradeoff:** Audio Session is currently a progressive enhancement rather than a cross-browser API. Media Session metadata and actions do not grant background execution. On an installed mobile PWA, minimizing the app or locking the screen may stop outgoing microphone capture even while incoming audio continues. Users who require uninterrupted outgoing audio must keep Towk in the foreground. Mobile operating systems may freeze, suspend, or terminate a hidden PWA and its microphone capture; a service worker cannot own a live `MediaStream`. Guaranteed Android background calling requires a native foreground-service/communication-device integration, and guaranteed iOS background calling requires native audio-session capabilities. Towk restores the web call when the page resumes but cannot honestly promise native-app background capture from a PWA alone. Browsers may also reject Wake Lock for battery or policy reasons, omit call-specific Media Session actions, or require a transient user gesture for Picture-in-Picture.

### 17. Camera capture preserves the sensor frame before adapting quality

**Decision:** Camera capture uses ideal 1280 × 960 and 30 FPS constraints so mobile browsers can select a 4:3 sensor mode instead of a tighter 16:9 crop. When `getSupportedConstraints()` exposes `resizeMode`, Towk requests exact `none`; a driver rejection scoped to that constraint retries once without it. Publication uses VP8 simulcast and frame-rate-preserving degradation, while receiving uses LiveKit adaptive stream and dynacast. Device refresh replaces a disappeared selection, technical mobile camera labels are mapped to lens roles, and the local tile cycles exposed lenses without leaving the call.
**Why:** A fixed 16:9 capture preset can make a browser crop a 4:3 phone sensor before Towk receives the track, so CSS `object-fit: contain` alone cannot recover the lost field of view. A 4:3 1280 × 960 target preserves the natural phone-camera frame while retaining a 720p-class quality envelope after adaptive publication. The standard `resizeMode: none` instruction makes the no-crop intent explicit on compliant engines.
**Tradeoff:** Browsers decide which physical lenses they expose and may group or label them differently; a pure PWA cannot force an unexposed ultra-wide lens. Exact field of view, resolution, frame rate, and lens availability therefore remain physical-device acceptance items. This policy follows the [W3C Media Capture and Streams `resizeMode` constraint](https://www.w3.org/TR/mediacapture-streams/#def-constraint-resizeMode); browser support must be rechecked as engines evolve.

### 18. One global session projection owns call navigation and commands

**Decision:** The frontend projects the winning local call session across all registered servers and routes every join through one intent controller. The scene observes that session, while the dock and PWA/OS command handlers re-resolve its exact server store and call ID at invocation time. The Messages attention gate suppresses typing, composer interaction, read advancement, and voice-message capture while Call is selected. An in-progress voice-message capture rejects a call intent without losing its tracks; a review draft is handed back to the same room/thread composer.
**Why:** A route-scoped call card or DOM-driven join path can target the wrong server, duplicate admission, or mark hidden messages as read. A small global projection and local capture coordinator preserve existing server/media authority while making ownership explicit.
**Tradeoff:** The projection assumes one winning local session. If transient multi-window state exposes more than one candidate, connected outranks reconnecting, which outranks joining; every command still fails closed when the captured store or call generation is no longer current.

## Permissions

- `voiceCallToken` query — requires room membership.
- `callParticipants` query — requires room membership.
- `activeCallRoomIds` query — requires server membership.

Voice calling doesn't have a dedicated permission today; room membership is the gate.
